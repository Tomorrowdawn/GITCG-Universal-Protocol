\section{Introduction}

GITCG Universal Protocol, also known as \textit{GIUP}, is a descriptive
 definition of game Genius Invokation TCG \footnote{https://en.wikipedia.org/wiki/Genius\_Invokation\_TCG}. GIUP is committed to creating a universal, transferable definition of situations and actions for GITCG. GIUP isn't a rulebook for GITCG - it's not trying to be the boss here. Instead, GIUP's goal is to describe the current state of play in GITCG and the potential action space, without getting tangled up in how different elements interact. So, we claim it  \textit{descriptive}.
 
 \section{Basic Elements}
 
 This section will introduce the key terms in GITCG and provide precise definitions.
 
 \begin{term}{Player}
 	GIUP uses a number starting from zero to represent players. In the basic version, there are only two options: 0 or 1. In the extended version, there will be other options, such as a random player (2).
 \end{term}

\begin{term}{Current Player}
	Current Player represents the one who can take an action at now.
\end{term}
	
\begin{term}{Round}
	It is exactly same as Round in the game.
\end{term}

\begin{term}{Turn}
	When current player changes from 0 to 1 or 1 to 0, Turn +1. At the beginning of each Round, Turn is set to 1.
	
	This definition already takes special cases into account. 
\end{term}
	
\begin{term}{Element}
	Elements are:
	\begin{enumerate}
		\item[0.] Omni (also Empty for aura)
		\item Pyro
		\item Hydro
		\item Electro
		\item Cryo
		\item Dendro
		\item Anemo
		\item Geo
	\end{enumerate}
\end{term}

\begin{term}{Damage Type}
	Damage Types not only include \termref{Element}, but also three additional options: piercing, physical and healing. Omni damage has no practical meaning here.
	
	\textit{Healing is literally not a type of damage... but this definition makes life easier in many cases.}
\end{term}

\begin{term}{HP}
	HP is a non-negative integer.
\end{term}

\begin{term}{Energy}
	Energy is a non-negative integer.
\end{term}

\begin{term}{Dice}
	Dice is a pair: (\termref{Element} or Black or White, Number)
	
	We use term \textbf{Elemental Dice}\label{Elemental Dice} to refer dice with concrete \termref{Element}.
\end{term}

\begin{term}{Dice Pattern}
	Dice Pattern is an unordered list of \termref{Dice}.
	
	An example is [\(Pyro, 1\), \(Black, 2\)], which is a typical setting for Normal Attack of Pyro character.
\end{term}

\begin{term}{Skill}
	A skill consists of 
	\begin{enumerate}
		\item Skill Name. An identifier(string).
		\item \termref{Energy}.
		\item \termref{Dice Pattern}.
		\item Type. Normal Attack, Elemental Skill or Elemental Burst.
	\end{enumerate}
\end{term}

\begin{term}{Usage}
	Usage is a non-negative integer or positive infinity. It usually indicates how many times some effect can be triggered. For a permanent effect, it's positive infinity.
\end{term}

\begin{term}{Superscript}
	Superscript is a \termref{Usage} annotated in the upper right corner of some entity in game.
\end{term}

\begin{term}{Subscript}
	Subscript is a \termref{Usage} annotated in the lower right corner of some entity in game.
\end{term}

\begin{term}{Zone}
	A Zone consists of:
	\begin{enumerate}
		\item Metadata. A collection of information that is not indexed by Route:
		\begin{enumerate}
			\item Name
			\item Additional information specific to the Zone type
		\end{enumerate}
		\item Entity List. An ordered list of components that can be indexed by Route. Each component is either:
		\begin{enumerate}
			\item A Unit (any non-Zone entity)
			\item Another Zone
		\end{enumerate}
	\end{enumerate}

	The ordering of Entity List is significant as it determines the Route indices. Unless specified otherwise, the ordering is fixed or follows FIFO for variable-length lists.
\end{term}

\begin{term}{Equipment}
	\begin{enumerate}
		\item ID.
		\item Description. Text.
		\item Type. Weapon, Talent, Artifact, Technique or Other.
	\end{enumerate}
\end{term}

\begin{term}{Buff}
	\begin{enumerate}
		\item ID.
		\item Text description.
		\item \termref{Subscript}.
	\end{enumerate}
\end{term}

\begin{term}{Character}
	A Character consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item ID
			\item Aura (\termref{Element}). Empty by default
			\item \termref{HP}
			\item \termref{Energy}
		\end{enumerate}
		\item Entity List:
		\begin{entitylist}
			\item Equipment Zone (ordered by type: Weapon, Talent, Artifact, Technique, Other)
			\item Skill Zone
			\item Buff Zone
		\end{entitylist}
	\end{enumerate}
\end{term}

\begin{term}{Character Zone}
	A Character Zone consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item Player ID
			\item Active character index
		\end{enumerate}
		\item Entity List: an ordered list of \termref{Character}
	\end{enumerate}
\end{term}

\begin{term}{Support Zone}
	A Support Zone consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item Player ID
			\item Maximum capacity (4)
		\end{enumerate}
		\item Entity List: an ordered list of Support entities, where each Support entity contains:
		\begin{enumerate}
			\item Metadata:
			\begin{enumerate}
				\item Name
				\item \termref{Subscript}
				\item \termref{Superscript}
			\end{enumerate}
		\end{enumerate}
	\end{enumerate}
\end{term}

\begin{term}{Summon Zone}
	A Summon Zone consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item Player ID
			\item Maximum capacity (4)
		\end{enumerate}
		\item Entity List: an ordered list of Summon entities, where each Summon entity contains:
		\begin{enumerate}
			\item Metadata:
			\begin{enumerate}
				\item Name
				\item \termref{Damage Type}
				\item \termref{Subscript}
				\item \termref{Superscript}
			\end{enumerate}
		\end{enumerate}
	\end{enumerate}
\end{term}

\begin{term}{Dice Zone}
	A Dice Zone consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item \termref{Player}.
			\item Count K.
		\end{enumerate}
		\item Entity List: an ordered list of \textbf{Elemental Dice}
	\end{enumerate}
\end{term}

\begin{term}{Card}
	\begin{enumerate}
		\item ID.
		\item Text description.
		\item \termref{Energy}.
		\item \termref{Dice Pattern}.
	\end{enumerate}
\end{term}

\begin{term}{Hand Zone}
	A Hand Zone consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item Count K.(10 maximum)
		\end{enumerate}
		\item Entity List: An ordered list of \termref{Card}

	\end{enumerate}
\end{term}

\begin{term}{Pile}
	A Pile consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item \termref{Player}.
			\item Count K.
			\item A ordered list of positions(-1 for unknown, or 0 to M-1 from top to bottom)
		\end{enumerate}
		\item Entity List: an ordered list of \termref{Card}.
	\end{enumerate}
\end{term}

\begin{term}{Player Area}
	A Player Area consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item \termref{Player} ID
			\item Arcane Legend status
		\end{enumerate}
		\item Entity List:
		\begin{entitylist}
			\item Character Zone
			\item Team Buff Zone
			\item Support Zone
			\item Summon Zone
			\item Dice Zone
			\item Hand Zone
			\item Pile
		\end{entitylist}
	\end{enumerate}
\end{term}

\begin{term}{Game}
	A Game consists of:
	\begin{enumerate}
		\item Metadata:
		\begin{enumerate}
			\item List of \termref{Player}
		\end{enumerate}
		\item Entity List:
		\begin{entitylist}
			\item Two \termref{Player Area}
		\end{entitylist}
	\end{enumerate}
\end{term}

\begin{term}{Route}
	Each unit/Zone is indexed by a unique route.
	
	A Route is a series of indices separated by dots. It starts from \termref{Game} and goes down until reaching the \termref{Zone}/Unit you want to specify. 
	
	For example, \texttt{0.2} refers to the Summon Zone of Player 0.
	
	\texttt{0.2.1} refers to the 2nd summon of Player 0.
	\texttt{0.0.0} refers to the 1st character of Player 0.
	\texttt{0.0.0.0.0} refers to the Weapon of the 1st character of Player 0.
	
	For cards in the pile , indices directly correspond to their actual order, but you typically shouldn't specify Cards in the pile directly by index unless you know their actual positions.
	
	In implementation, we recommend binding the corresponding Route to all entities that have been described. This can also be referred to as their Address in the game.
\end{term}

\section{Game Flow}

The Game starts off with \termref{Player} 0. \termref{Current Player} can perform Actions. The rule of player switch is out of the scope of GIUP.

\begin{term}{Action}
	\begin{enumerate}
		\item Type. Select, End, Confirm, Surrender.
		\item Route. The target's route which is selected. None for other types of actions.
	\end{enumerate}

	This definition is highly abstract because we declare GIUP to be descriptive. We will explain how it can be properly implemented to correctly execute normal GITCG operations. For example, when you want to play a card from your hand, you first need to use Select to choose that card, then repeatedly use Select to choose the corresponding dice, and finally use Confirm to execute. Since Route indexes all selectable entities, you can always complete the same operations as in GITCG through Select (just like clicking on your phone), and then finally execute it through Confirm. The definition itself doesn't involve these implementation details, so it is implementation-independent.
\end{term}

\section{Random Extension}

This section we introduce a random player and describe how to control the random events. This extension is denoted as GIUP-R.

\begin{term}{Random Player}
	We use -1 to refer to this random player.
	
	After the execution of Confirm \termref{Action}, \termref{Current Player} is changed to -1.
\end{term}

Since the rules for action execution are beyond the scope of GIUP, we need to additionally state here how to properly implement the random player to control random events. For instance, when Player 0 needs to draw cards, the Current Player will be switched to Random Player, and the Random Player decides which cards are drawn. This extension will be supplemented later to cover possible Random Player actions. The most significant benefit of doing this is that players can make predictions by controlling the random player - for example, players can calculate optimal strategies by assuming which cards the opponent holds(assume random player has an action: SetOppoHand).
